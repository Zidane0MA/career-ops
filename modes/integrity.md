# Mode: integrity

Pipeline data-integrity audit and repair.

**Source of truth hierarchy:** `reports/*.md` > `data/pipeline.md` > `data/applications.md`.
Reports are generated by the evaluation engine and are never batch-shifted; pipeline entries are written at scan time and are generally correct for URL/company/role; applications.md is the most downstream and most prone to batch-insertion errors.

## Phase 1 — Scan (always run, never write)

First, run `node audit-pipeline.mjs` and parse the output. This script performs 12 checks:

> **Note (Windows/PowerShell):** Scripts emit ANSI color codes. If output is garbled, redirect to file: `node audit-pipeline.mjs > audit.txt 2>&1` and read with `view_file`. On PowerShell use `node audit-pipeline.mjs | Out-File -Encoding utf8 audit.txt`.

| Check | Severity | What it detects |
|-------|----------|-----------------|
| 1. Corrupt lines | ERROR | Malformed rows (fragments like `304 \|`) |
| 2. Duplicate IDs | ERROR | Same `#NNN` appears twice in pipeline or applications |
| 3. Pipeline → Apps gap | ERROR | `#NNN` processed in pipeline but missing from applications |
| 4. Apps → Pipeline gap | WARN | Entry in applications without pipeline entry (normal for direct evals) |
| 5. Cross-ref mismatch | ERROR | `applications.md` row `#NNN` links to report `#MMM` where `N ≠ M` |
| 6. Missing report file | ERROR | Report referenced in applications but file missing from `reports/` |
| 7. Orphan reports | WARN | Report file on disk not referenced by any applications row |
| 8. Missing JD file | ERROR | Pipeline `local:jds/xxx.md` URL points to nonexistent file |
| 9. Remote URL info | INFO | How many remote URLs have local JD copies |
| 10. Score mismatch | WARN | Score differs between pipeline and applications for same ID |
| 11. PDF flag mismatch | WARN | PDF ✅/❌ differs between pipeline and applications for same ID |
| 12. Duplicate reports | WARN | Multiple reports share the same **URL:** field (applied twice or duplicate eval) |

**CRITICAL:** Debes presentar los resultados de TODOS los 12 checks como una tabla Markdown al usuario. NO truncar la tabla — si un check tiene 0 findings, muestra "✅ OK" en su fila, no lo omitas. Si 0 errors + 0 warnings → `✅ Pipeline integrity verified.`

Next, run `node audit-jds.mjs`. This script performs deep JD file checks:
- **Title/URL Duplicates:** Detects if multiple JDs point to the same role/URL.
- **True Orphans:** JDs in `jds/` that have no path reference and no URL reference. (Candidates for deletion).
- **Soft Orphans:** JDs physically present, but the reports or pipeline link them via an external URL instead of `local:jds/...` (Needs link fix).
- **Format Warnings:** Missing H1 titles or missing `**Apply:**` fields.

**CRITICAL:** Debes presentar los resultados de auditoría JD como una tabla Markdown al usuario justo después de la tabla anterior. Sólo incluye filas donde haya hallazgos. Añade una columna "Linked to" cruzando el nombre del archivo con pipeline.md y applications.md:

| Issue | File | Linked to | Action |
|-------|------|-----------|--------|
| Title dupe | `file.md` | #NNN Company · Score · Status ✅/❌ | keep / delete |
| True orphan | `file.md` | — | delete |
| Soft orphan | `file.md` | #NNN (URL ref only) | fix link in report |
| Missing H1 | `file.md` | #NNN Company | investigate (line 1: "…") |
| Missing Apply | `file.md` | #NNN Company | investigate |

If 0 issues → `✅ JD integrity verified.`
If 0 JD files scanned → `ℹ️ No JD files in jds/ — nothing to audit. Remote-only pipeline.` (this is NOT "integrity verified" — it means there are no JDs to check).

## Phase 2 — Diagnose (classify issues, plan fixes)

### Pre-classification: cross-check all findings (MANDATORY)

Before classifying any individual finding into a Strategy, cross-reference related checks **using all three data sources** (`data/pipeline.md` processed entries, `data/applications.md`, and `reports/`) to avoid misclassification:

1. **Orphans × Duplicate URLs × Pipeline presence (Check 7 × Check 12 × pipeline.md):** For each orphan report:
   a. Check if its URL matches another report that IS referenced in applications. If yes → **superseded** (Strategy I).
   b. Check if the orphan has a corresponding `[x] #NNN` entry in pipeline.md. If the orphan has NO pipeline entry but the URL-matching report DOES → this confirms superseded status (the orphan was a first-pass artifact replaced by the pipeline-tracked re-evaluation).

2. **Pipeline gaps × URL matching (Check 3 × Check 12 × pipeline.md):** For each pipeline gap ID `#NNN`:
   a. Read the URL directly from pipeline.md's `[x] #NNN | {URL} | ...` entry — this avoids opening the report file.
   b. Check if that exact URL appears in any existing applications entry (via its report's `**URL:**` field or via another pipeline entry with a different ID).
   c. If yes → this is a duplicate/re-eval, NOT a true gap. Classify as Strategy I or H (MANUAL).

3. **Pipeline gaps × Apps gaps (Check 3 × Check 4):** If `#NNN` is in pipeline-gap AND a different `#MMM` for same company+role is in apps-gap → compare their URLs in pipeline.md. If same URL → confirmed ID reassignment from batch re-evaluation.

4. **Pipeline entry as provenance signal:** A report WITH a pipeline entry was created through the normal scan→batch→evaluate flow. A report WITHOUT a pipeline entry was created ad-hoc (manual eval, first-pass batch artifact, or direct URL evaluation). When two reports share a URL, the one WITH the pipeline entry is generally the canonical evaluation.

> **Why this matters:** Without cross-checking, agents treat each finding in isolation and produce incorrect fix plans (e.g., integrating 17 superseded reports as new tracker rows when they should be flagged for cleanup). Using pipeline.md's URL field directly also avoids unnecessary report file reads.

After cross-checking, classify each remaining issue into one of these fix strategies before touching any file:

### Strategy A — Data-shift repair (Checks 5, 10, 11)

**Pattern:** A batch insertion wrote applications rows in wrong order, so row `#NNN` contains data (company, role, score, report link, notes) that actually belongs to a different ID.

**Detection:** Check 5 fires (cross-ref mismatch) AND the report file the row points to exists on disk but belongs to a different ID.

**Resolution:**
1. Read the report `reports/NNN-*.md` (matching the row's ID, not the wrong link).
2. Extract from it: company, role, score, date, PDF status, recommendation note.
3. Rebuild the row using report data as truth.
4. If the report file `NNN-*.md` doesn't exist on disk → can't auto-fix, flag for user.

### Strategy B — Empty-field fill (Checks 5 aftermath)

**Pattern:** After Strategy A, some rows have correct report link but empty company/role/notes fields.

**Detection:** Row has `reportRef == id` (correct link) but company or role column is empty.

**Resolution:** Parse the report's header to extract company, role, notes. Fill the empty fields.

**Report title parsing** — Reports use multiple title formats. Parse in this order:

1. `# Evaluación: Company — Role` or `# Evaluation: Company — Role`
2. `# Evaluación — Role · Company` (middle-dot separator, no colon)
3. `# NNN — Company · Role` or `# NNN — Company | Role` (numbered)
4. `# Role — Company` or `# Company — Role` (detect by keyword heuristics)

For format 4, use these heuristics to detect which side is the role:
- **Role keywords at start:** Técnico, Administrador, Ingeniero, Operador, Developer, Support, IT, Cloud, DevOps, Help Desk, Systems, Backend, Helpdesk, Hardware, SysOps, Software
- **If left starts with role keyword** → left = Role, right = Company
- **Otherwise** → left = Company, right = Role
- **When title has multiple dashes** (`Role – Subtitle — Company`), split on the LAST em-dash

### Strategy C — Score/PDF normalization (Checks 10, 11)

**Pattern:** Minor formatting differences between pipeline and applications.

**Resolution:**
- For score: the report's `**Score:**` field is truth. Normalize both pipeline and applications to match.
- For PDF: the report's `**PDF:**` field is truth. `✅` or a `.pdf` file path = generated. `❌` = not generated.

### Strategy D — Orphan report integration (Check 7)

**Pattern:** Report file exists on disk but no applications row references it.

**Detection:** File `reports/NNN-*.md` has no matching `[NNN](../reports/NNN-...)` link in applications.

**Resolution:**
1. Parse the report header (date, company, role, score, PDF, legitimacy).
2. Check if `#NNN` already exists as a row in applications — if yes and the row just has a wrong report link, fix the link (Strategy A).
3. If no row exists at all, build one from report data and insert at the correct position (descending ID order).
4. **Exclude from action:** files matching `pattern-analysis-*.md` or `.gitkeep`.

### Strategy E — Pipeline gap fill (Check 3)

**Pattern:** Pipeline has `[x] #NNN` but applications has no row for it.

**Resolution:**
1. First, check if report `NNN-*.md` has a `**URL:**` that matches any existing applications entry (via a different report). If yes → this is a duplicate/re-eval, not a true gap. Classify as Strategy I (superseded) or Strategy H (MANUAL) instead.
2. If no URL match, build applications row from report data (same as Strategy D). If no report exists either, flag for user.

### Strategy F — Corrupt line removal (Check 1)

**Pattern:** Fragment lines like bare `304 |` from broken copy-paste.

**Resolution:** Remove the line.

### Strategy G — JD Maintenance & Soft Orphans (`audit-jds.mjs` aftermath)

**Pattern:** JDs are fully downloaded but not properly linked, lack standard formatting, or are completely abandoned.

**Resolution:**
- **Soft Orphans:** Edit the offending `reports/NNN-*.md` file. Replace its `**URL:** https://to.indeed.com/...` with `**URL:** local:jds/{filename.md}`.
- **Missing H1:** Open the JD file and prepend a `# {Title}` derived from the report or file name.
- **True Orphans:** Delete the files from `jds/` after verifying they truly belong to no active application process.
- **Duplicates:** If the same URL has two local JDs, verify if they belong to different tracker IDs (user applied twice). If so, keep both. If it's a true redundant duplicate for the same ID, delete one and ensure the report points to the remaining one.

### Strategy H — Informational only (Checks 4, 8, 9)

**Pattern:** Apps without pipeline entry (normal), missing JD files (needs rename or re-download), remote URL info.

**Resolution:** Report to user, don't auto-fix.

### Strategy I — Superseded report cleanup (Check 7 + 12 intersection)

**Pattern:** Report exists on disk, not referenced in applications, AND its URL matches another report that IS referenced. This means a re-evaluation was done and the newer report replaced the older one.

**Detection:** Orphan report `NNN-*.md` has same `**URL:**` as referenced report `MMM-*.md` where MMM > NNN (newer eval).

**Resolution:** Flag for user with options:
1. Delete orphaned superseded reports
2. Move to `reports/archive/`
3. Keep as-is (no integrity impact, just disk clutter)

**Never auto-delete reports.** Only the user deletes reports. For proactive cleanup selection, use `modes/clean.md`.

## Phase 4 — Apply fixes (after user confirms)

### Execution order

Apply fixes in this exact order. Each step reads the current state of the files (not a cached version):

1. **F + A + B + C — Run the fix script** (handles corrupt lines, data-shift, empty fields, score normalization in a single pass):
   ```
   node fix-pipeline.mjs --apply
   ```
2. **D + E — Add missing rows** (orphans + pipeline gaps, manual agent work — see strategies D and E above)
3. **G1 + G2 + G3 — JD Maintenance** (fix soft orphans, add H1s, delete true orphans)
4. **I — Superseded report cleanup** (present options to user, apply their choice — never auto-delete)

### Write protocol

- **Backup before any write:** `fix-pipeline.mjs --apply` creates `pipeline.backup-{ISO-timestamp}.md` and `applications.backup-{ISO-timestamp}.md` automatically. For manual D/E edits, create the backup yourself first.
- **Edit applications.md directly** (this is a repair operation, not a normal tracker addition — TSV protocol from `_shared.md` rule 9 does NOT apply to integrity fixes).
- **Never delete report files during auto-fix.** Only delete reports when the user explicitly confirms cleanup; proactive cleanup belongs in `modes/clean.md`.
- **Deletion consistency rule:** If the user explicitly confirms deleting an entry while in integrity mode, remove that ID consistently from all three layers: `reports/{NNN}-*.md`, `data/pipeline.md`, and `data/applications.md` when present. Do not leave dangling references.
- **Pipeline.md edits** are limited to score normalization or confirmed deletion cleanup. Don't change URLs, company names, or PDF flags in pipeline — those are user-controlled.

### Row construction

When building a row from report data:

```
| {id} | {date} | {company} | {role} | {score} | {status} | {pdf} | [{id}](../reports/{filename}) | {note} |
```

Where:
- `{status}` = inferred from report body: if score < 2.0 or body contains "SKIP"/"no aplicar"/"suspicious" → `SKIP`. Otherwise `Evaluated`.
- `{pdf}` = `✅` if report's `**PDF:**` field contains a `.pdf` path or starts with `✅`. `❌` otherwise.
- `{note}` = first bold recommendation found: `**APLICAR...**`, `**NO APLICAR...**`, `**SKIP...**`, `**BORDERLINE...**`. Truncate to 120 chars.

## Notes

- **Re-evaluations** are NOT errors. If `notes` contains `Re-eval` and the report link points to a different (newer) report number, this is by design. The row keeps its original `#NNN` but links to the re-evaluation report.
- **Superseded reports** (old reports replaced by re-evaluations) should NOT be added back to the tracker. If an orphan report's ID has a more recent report for the same company/role, mark it as superseded and skip. See **Strategy I** for the formal handling procedure.
- **This mode does NOT run `_shared.md`** — it's a maintenance operation, not an evaluation.
- **Idem for `verify-pipeline.mjs`** — that script checks format validity (canonical statuses, score format, row structure). Run it after integrity fixes for a second-layer validation: `node verify-pipeline.mjs`.
